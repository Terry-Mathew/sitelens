- Mode: fallback only. No Firecrawl, Upstash, or PageSpeed key was set. Only `ACCESS_CODE` and `SESSION_SECRET` were set in a git-ignored `.env.local`.
- Local dev server. Login worked. Without a session, `POST /api/scan` returned 401 and `/` returned a 307 redirect.

- One homepage request per site through `/api/scan`. All six scans finished within 14 s. Every scan had `loadedWith: direct-fallback` and the limitation `firecrawl_unavailable`.

## Suspected false findings

I verified findings 1 and 2 by reading the check code and the saved evidence. I did not send extra requests to the sites to confirm the rest (one request per site, and a request that imitates a browser was refused). Treat 4 to 6 as unconfirmed.

1. **contact-method passes on any `<form>` (wordpress.org, react.dev, squarespace.com). False pass, likely.** The evidence shows `form: true` with no phone, no email link, no contact page link, and no messaging. `lib/checks/conversion/contact-method.ts` counts `$('form').length > 0`. A search form or newsletter form counts as a way to contact the business. On wordpress.org and react.dev the form is very likely a site search form. The pass tells a client that contact is easy when SiteLens did not show it.
2. **favicon passes when the icon link is an empty data URI (example.com). False pass.** Evidence: `linkTag: true, icoStatus: 404`. The page has `<link rel=icon href=data:,>`, which is a deliberate empty icon. `lib/checks/technical/favicon.ts` accepts any `rel=icon` link without checking `href`.
3. **no-js-content passes in fallback mode when `jsRendered` is false (all five scans where the check ran).** Evidence is only `{ rawWords }`. Without a rendered copy, SiteLens cannot compare raw and rendered text, so a pass is not proof. neverssl.com passed with `rawWords: 1`, which is a page that has almost no content in the raw HTML. A pass on missing data breaks product rule 3. The check should return unable_to_check, or show the limitation, when there is no rendered copy and the raw page is very short.
4. **g2.com (blocked homepage): sitemap fail (warning) with evidence `url: https://www.g2.com/llms.txt`, state invalid. Probably false.** A sitemap warning points at an `llms.txt` address. This looks like a bot-challenge page that returns HTTP 200 for any path being read as real content. The fail is shown to a client as fact while the rest of the site is unreadable.
5. **g2.com: favicon pass (`linkTag: false, icoStatus: 200`), robots-present, robots-allows pass, ai-crawlers observation, and llms-txt present: true. Possibly false.** The homepage was blocked, but these checks read other paths that returned 200. If the site serves the same challenge page for every path, none of these is a real `robots.txt`, `llms.txt`, or icon. I did not confirm this. A scan marked `homepage_blocked` should probably not trust other paths either, or should say so.
6. **analytics fail on squarespace.com (tools: []) and structured-data / analytics on JavaScript-heavy sites. Possibly false in fallback mode.** The raw HTML may not contain analytics scripts that a script manager adds later. This is expected to be a limit of fallback mode, but the finding is a fail, not unable. Not confirmed.
7. **img-alt fail on squarespace.com: 1 of 77 images, example `(no src)`. Weak finding.** An `<img>` with no `src` is probably a lazy-loading placeholder, not a visible image with missing alt text. The evidence is true, but a client may read it as a real fault.
8. **neverssl.com: https is Critical.** This is true (the site is http-only by design). It is listed because the severity is correct only when the site is a business site. No change needed.

Other observations (not false findings):
- Several checks use fail/opportunity for normal choices (for example click-to-call on a site with no phone number). This is by design.
- example.com `title` fails as "opportunity" for a 14-character title. This follows the length rule.
